## Annotation boundaries

A Project denotes a solution, product or initiative. Membership requires explicit dedicated purpose or a documented relationship. A generic workload on Kubernetes is not automatically a Kubernetes component; mentioning Keycloak as a supported login option is not enough to place a generic app in the Keycloak initiative. Owner equality, a dependency or a README keyword alone is insufficient. Dedicated extensions and clients can qualify when their purpose is unambiguous. Domains derive through proposed Project parent relationships, not from collection buckets. Topics capture primary reusable capabilities. Tags capture primary implementation technologies, preferably corroborated by manifests rather than every dependency listed.

Every relationship requires an exact supporting passage, source path, commit, blob SHA and line/character span. Record explicit exclusions, uncertainty and contradictory versions separately. Absence of a claim means unknown membership, not a negative. Missing license information is a flagged source condition, not permission to republish. README and supporting files remain local in the ignored private corpus directory; no complete source snapshots are published.

## Collection protocol

Use the parent's credential-isolated local broker and shared admission ledger. Do not inspect credentials or environment files. Store full commit-pinned READMEs and up to four purpose/architecture/manifest/relationship files per accepted repository. Read saved content before proposing references. Do not execute collected code, clone histories, invoke paid models, mutate GitHub or change existing application/benchmark state.

Keep search provenance, immutable source metadata, complete README snapshot retention and honest semantic read coverage, source hashes and evidence visibility distinct. Supporting docs inform reference review but must not silently enter the application's current README-only inputs. Retain metadata-only and thin README challenges explicitly; replace inaccessible or oversized README candidates rather than truncating them.

## Findings that affect evaluation

Project membership must distinguish dedicated integrations from runtime dependencies, owner names, alternatives and comparisons. Examples include a Backstage-owned generic MkDocs plugin with UNKNOWN Backstage membership, a Keycloak alternative that is not part of Keycloak, and a dedicated OpenTofu extension with explicit OpenTofu and Visual Studio Code relationships. Source-derived decisions and the current application inputs are tracked separately.

Lineage should influence splitting even when GitHub reports `fork: false`: Terraform/OpenTofu shared lineage, Kubernetes staged repositories, translated agent-tool documentation, generated clients, mirrored providers and VS Code distribution/build repositories all create related-source leakage risks. The dossiers flag these relationships for aggregate split-group review.

Repository artifact type also matters. Feedback hubs, docs repositories, closed-source scanner support repositories, generated clients, language-server clients and platform deployment configurations are not interchangeable with product implementations. Primary-language metadata is retained as an as-of shared input, not asserted as independent technology truth; generated Makefile/Mustache or bundled C code can obscure the actual API language.

Performance, certification, security and comparative marketing statements in READMEs were not independently benchmarked. Thin purpose descriptions and purpose text under unusual headings are recorded as extraction challenges. Missing or ambiguous license information remains flagged rather than treated as permission to republish full source.
