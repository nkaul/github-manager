# Product experience, demos and publication

## Make system state understandable

Design the user's path through sync, browsing, review and correction before exposing infrastructure. Scope counters to the current selection and label them accurately. “Unclassified” is misleading when the real condition is “No Project” despite accepted Topics/Tags. Show analysis outcome, coverage, freshness and review separately when they can differ.

Prioritize the primary navigation. GitHub Manager moved AI organization/content sync to the header, gave the concept tree more room, added Topics/Tags alongside Domains/Projects, and made optional top-nav repository fetches occur only on demand. Compact KPI cards, readable consistent type, meaningful icons, rounded chips and clear filter controls improve the workflow without changing its data model.

Follow the chosen visual system consistently across progress, errors and status text. The case's balanced Deep Purple, Purple, Indigo, Blue and Light Blue direction replaced an overuse of purple. That palette is a project preference, not a universal system-design requirement. Configurable Zen-cat icons and reduced-motion alternatives likewise belong to this product's identity.

## Corrective interactions

Explain collisions with the exact conflicting value, owner and reservation status, including hidden drafts/reservations when applicable. Offer manual correction and user-selected remediation. A helpful error should not quietly rename or merge a concept. Review actions should retain user rejection precedence and show stale/conflicting selections.

Provide bounded cohort selection by count or filters as well as manual selection. Preview the exact repositories across all pages and explain skipped/analyzed/private-policy exclusions. Drag-and-drop adds membership to supported concept types; provide an equivalent keyboard/touch action. Derived relationships update locally rather than invoking another model.

## Demos as behavioral evidence

A full feature walkthrough needs a scenario order, rehearsal and checkpoints, not only a runbook. Use the real current UI and an appropriate recording canvas; 1080p output alone does not prove all content fits in the capture. Confirm viewport, scaling, readable labels, player output and screen bounds. Keep sign-in/authorization outside recording unless explicitly intended.

Respect approved data visibility. The user may authorize a real connected account and unmasked content; do not substitute synthetic material unnecessarily or assume that this permission applies to future unrelated exports. Use an isolated copy for destructive rehearsal when it preserves realism and the live workspace.

Narration should announce each section and its purpose before the mechanism. Build visible state changes from text, not only camera pans over static diagrams. Match speech segments to readable motion, keep pauses for complex transitions and test actual playback. A selected natural voice is still synthetic; do not imply it is a human recording. Fixed duration, ASR coverage or average words/minute is not proof of perceived pacing. Carry user feedback into the next version.

## Publication handoff

Distinguish the application, its demo site and article/media sources. A demo-only GitHub Pages repository does not deploy the backend. Preserve previous academic/illustrated/article editions when requested; explain the problem and show actual input/augmentation/model-boundary examples rather than reducing insight to make prose shorter.

Review external media permissions separately from local playback. A public Drive embed does not authorize copying the file into a public repository. GitHub Manager's user chose Drive audio embed only; preserve source links and test the live embed behavior. Publish only the concrete authorized artifacts and verify the resulting page. Header motion should remain readable and respect reduced motion.

For a visual explanation, compose with the illustration skill if available; for an independent article, compose with the writing skill. Keep implemented versus proposed status visible in both. A friendly illustration must cover the technical content, and an engaging article must retain its evidence and qualifications.
